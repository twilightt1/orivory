ENTRY 001 The shape Rejected: walled garden

Where does your AI's memory actually live?

Here: on hardware you own, in a directory you can copy. One container holds the API, the MCP hub, the SQLite database, an embedded vector store and your uploads — no Postgres, no Redis, no object store, no worker. Nothing to sign into either: the install has exactly one identity, the local owner, and agent tokens are the only credentials.

"A request with no Authorization header IS the local owner. Nothing to log in to, nothing to expire, no 401 for a missing token." — docs/API.md §1
"An agent token acts as that client on the MCP endpoint and on POST /api/v1/imports, which is where the token's scopes are enforced and where every write is recorded in the access ledger under it." — docs/API.md §1

Account auth, chat, admin, analytics, sources and workspaces were removed with the full-stack product — the surface you can call is what GET /openapi.json lists. No cloud tier gates the governance features: the ledger, the scoped tokens and the receipts are the free core, because they are the point.

ENTRY 002 The mechanism vs. the field

One brain. Every agent knocks first.

Your memories live once — in SQLite and an embedded Qdrant folder inside the container's /data volume. Agents never "have" your memory. They request it through a scoped token, and the hub writes down the visit.

What agents get: search_memory · timeline · get_memory · list_recent under memory:read, and add_memory · correct_memory · delete_memory · forget_memory under memory:write — eight tools, and that is the entire surface. A token with only memory:read cannot write.

Ledger actions: mcp_search · mcp_get · mcp_list · mcp_add · mcp_correct · mcp_delete · mcp_forget (plus import for an agent-token upload). The ledger is append-only and survives erasure by design: it records that a memory was accessed before it was deleted, which is what makes it an audit trail.

Salience, not landfill. Memories that get recalled grow stronger; ignored ones fade. GET /api/v1/memories/digest resurfaces what you saved recently, and what you saved on this day in a previous year.

ENTRY 003 Erasure, honestly Verified by readback

Two kinds of forgetting. Both leave a receipt.

The word "delete" hides two different operations, so Orivory names them separately — and neither one pretends to be more than it verifies.

Capability Hard erase Soft forget
How to call it DELETE /api/v1/memories/{id} · POST /api/v1/erasure-receipts · MCP delete_memory MCP forget_memory
Rows Deleted, with the derived closure (children, links) Invalidated in place — content and provenance stay readable as history
Vectors Purged, then re-queried for residual The point stays; its payload state is refreshed to invalidated by the index drain
Re-import — Every affected source gets a suppression row, so the import path refuses it
What the receipt proves Absence readback: the vectors and rows are gone (completed) Serving readback: no target is visible to a serving surface any more
Access ledger Kept — append-only audit Kept — append-only audit

The honest limit: v0 verifies erasure by absence-checks. It does not probe whether a fact can be re-inferred from correlated knowledge-graph data, and entity/relation nodes themselves survive a memory erasure (their link counts are recorded in the receipt). Receipts whose readback could not confirm absence are stored as completed_unverified and re-checked by the reconcile pass that rides the index drain loop; a receipt is never upgraded by guesswork.

ENTRY 004 Ninety seconds, start to agent Pass: first run

Two commands. Then give it an agent.

01 · Boot the hub1 container
# whole hub: SQLite, in-process vectors, /mcp
docker run -d --name orivory -p 127.0.0.1:8000:8000 \
  -v orivory-data:/data \
  ghcr.io/twilightt1/orivory:lite

# or: docker compose up -d  (the same single service)
02 · Mint an agent tokenshown once
curl -X POST http://localhost:8000/api/v1/agents \
  -H "Content-Type: application/json" \
  -d '{"name": "Claude Desktop",
        "scopes": ["memory:read",
                   "memory:write"]}'
# → {"token": "oa_9f3c…"} — keep it

ENTRY 005 What it trades away Rejected: scale theatre

One container is a choice, not a footnote.

Everything below is a consequence of the single-container shape. If you need any of it, Orivory is the wrong tool and these docs say so first.

single-instanceone owner

No horizontal scale

SQLite and process-local caches do not fan out, and the embedded Qdrant store owns its folder exclusively — keep workers at 1, and put one container on one machine.

no brokereager tasks

No task queue

Work runs inline in the API process. A crash mid-task loses that task — anything a write enqueued into the index outbox is replayed by the drain loop on the next run, so SQL stays the truth.

first bootmodel cache

The first boot may download the embedding model

Boot warms the local ONNX session before anything is served, so a fresh volume fetches snowflake-arctic-embed-xs (~90 MB) first — with no timeout. Pre-seed the model cache when that matters, or set EMBED_WARMUP_ON_BOOT=false to pay a cold session on the first request instead.

cachesprocess-local

Memory that does not survive a restart

Rate-limit windows and caches live in an in-memory Redis shim: a restart drops them. Durable state is the SQLite file, the Qdrant folder and /data/uploads.

surfaceagents first

No web UI in the image

The Next.js frontend is not shipped: the product is the API plus the MCP hub, aimed at agents. /mcp is localhost-bound as shipped (DNS-rebind protection is on); set MCP_HUB_ALLOWED_HOSTS to expose it behind a proxy.
